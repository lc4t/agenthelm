## 版本检查应该回答的问题

功能 PR 应回答：改动是否有合法声明、测试是否通过、有没有擅改正式版本与生成物。它不应提前替所有并行分支分配相同的“下一个补丁版本”。

发布阶段应回答：从上一个正式发布 BOM 加上全部待发声明，是否能确定性地重算出当前计划；生成载体、迁移、产物和 tag 是否与计划一致。版本来自发布计划，CI 只验证计划和结果，不靠代码里预写一个下次版本。

当前 `dev` 仍使用 `release_meta.py --since "$(git describe --tags --abbrev=0)"`。它把功能合入与发布要求混在一起，迫使每个分支提前改版本与生成清单；`git describe` 又取最近可达 tag，可能得到 rc，或漏掉只在 main 合并提交上的正式 tag。现存 `v6.11.0` 位于 main 的合并提交，而 dev 的 describe 返回 rc.3，已经展示了这个差别。

[PR62](https://github.com/lc4t/agenthelm/pull/62) 负责分开变更片段门禁和发布计划门禁。推送门禁必须比较真实的推送前后提交；在干净 checkout 里拿 HEAD 和 HEAD 比，不能验证这次提交有没有遗漏声明。发布计划还必须绑定实际发布源码，防止生成计划后又改代码而绕过声明。

## 本次共同基线修复的范围

公共测试修复进入独立 PR，避免只散落在功能分支。历史 tag、schema、协议和工具链 pin 均保留。各套件在环境准备成功后继续收集结果，任一失败仍使 job 失败；不使用 `continue-on-error`。

这份测试修复不生成正式版本、不归档片段、不发布、不合并。发布流程结构调整在 PR62 单独审阅；现有功能分支按旧门禁携带的版本元数据，在切换门禁时仍需迁移为变更片段。
