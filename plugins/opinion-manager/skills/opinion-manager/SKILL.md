# Opinion Manager（Agent 行为规则管理）

将用户确认的表达、判断、协作、交付和设计要求管理为完整、可编辑的 `OPINION.md`。公开模板是可选偏好；用户确认的正文是当前环境的权威内容。个人 Profile（个人配置）与锁用于精确核验和离线重建。

`agents-init` 创建项目契约；本 Skill 管理规则；`project-orchestrator` 管理 Task/Case 与 Git；`agent-pack` 管理安装。执行版本化工具前完整读取 [版本契约](../../references/versioning.md)；首次配置按 [首次使用说明](../../references/onboarding.md) 操作。

## 首次入口

先只给用户以下三个主选项和一个可选入口。用户已明确选择时直接进入对应流程，避免重复询问。使用 `../../runtime/opinion_manager.py catalog --catalog ../../catalog --output json` 核对实际可用内容；开始时不要求用户逐条回答全部规则。

1. **直接用我们的模板**：展示实际可用的场景模板名称、用途与精确版本，选择后直接生成完整预览。随包 `scenario/reviewed-project@1.0.0` 适合完整分析与项目交付，`scenario/concise-project@1.0.0` 适合简明沟通与项目交付。用户只说“直接用模板”时可将前者作为明确标出的预览默认，完整内容确认后才生效；用户明确要求简明表达时展示后者。不要默认全选平行变体。
2. **选择模板的部分条目**：展示选定模板的完整规则及可读编号，一次收集保留、排除或修改决定。尽量保留精确模板引用，通过 overrides 停用条目；直接选择原子规则时说明模板版本不会自动追踪。冲突集中为一次编号裁决。
3. **啥也不要，自己迭代**：保持已有规则和初始化占位文件，不建立空 Profile 或锁，不进行偏好访谈。用户以后提出明确规则时再走自定义生成和确认流程。

可选入口：**基于 Agent 已授权的记忆和使用记录提出候选规则**。只使用当前会话或用户已明确授权读取的记忆；先说明可用范围。不得默认扫描私有目录、外部应用或其他项目。区分明确要求、重复反馈、推测、项目事实和一次性任务；仅行为要求可进入候选。展示候选全文、适用条件、证据与冲突，证据不足的明确标为待验证。没有可用记录时说明缺口，允许从空白开始或由用户提供说明。重复次数不等于确认，候选不自动晋升；最终完整内容经用户确认后才建立新版本。

用户粘贴既有规则时直接整理为个人候选，无需再选择入口。保留原意与约束强度；项目事实、命令、依赖、权限和目录职责留在项目契约。

第一次展示完整规则预览时，简短提示用户：“这是一版可以开始使用的规则。后续可以根据实际任务和反馈增删、调整或换模板，无需现在一次想全。我们鼓励先使用再迭代；每次修改会先展示变化，确认后保存为新版本。”不要要求用户一次设计出全部长期偏好，也不要把尚未确定的选择强行补成规则。此提示不增加确认问题，不降低用户已确认规则和具体交付要求的约束强度。

## 一次内容确认，分别核验指纹

1. 只在目标项目的指定私有位置保存候选来源与预览。已有规则文件直接使用；避免复制多份相同个人正文。
2. 运行 `profile` 预览，检查来源、完整有效内容、差异与 `unresolved`。将返回的 `profile` 对象保存为明确标识的私有候选 JSON，供 compose 读取；这一步不发布正式 Profile。
3. 用候选 JSON 运行 `compose --profile <候选> --project <项目> --output json`。`blocked` 非空或有未解决冲突时先处理，不请求保存确认。
4. 一次展示完整 `OPINION.md`、选择与排除结果、来源版本、个人修改、差异及拟保存文件；提供完整 Profile 和锁的审阅入口。用户确认的是此完整结果，Agent 保存两份工具实际返回的 `confirmation_sha256`，分别对应 Profile 与 compose。
5. 写入前重新执行两份只读预览，核对内容和两项指纹与批准结果一致。有漂移时停下并重新展示变化，禁止用旧批准覆盖新内容。
6. 按原参数及 Profile 指纹保存不可变 Profile；再用正式 Profile 路径和 compose 指纹保存正文与锁。路径切换不改变其确认内容。指纹不得混用或自行计算替代工具返回值。
7. 完整读回三份文件，与获批预览逐字及结构核对，再运行 `verify`。两次工具写入分别校验；这套流程不保证三个文件构成一次系统事务。中断时报告真实状态，按版本契约恢复。

没有内容变化时不重复询问同一组规则。规则含义发生改变、未解决冲突或相关内容漂移时仍须用户裁决。模板系列各选一个变体，同一 slot 的相反偏好必须处理；`scopes` 是适用说明，Agent 判断实际场景，工具不提供自动业务路由。用户希望只在命中时读取场景规则时，按版本契约的「分层加载」准备声明文件，与规则一起预览和确认；核心范围、规则束划分和路由都属于需要用户确认的内容。

## 维护与个人修改

查看升级用只读 `updates`。使用 `profile --from-profile <旧文件> --version <新版本>` 精确选目标版本，保留自定义正文和 overrides。升级三方冲突展示 base/local/upstream 的完整内容，集中由用户决定。按一次内容确认流程生成新正文。禁止默认采用 latest、修改已发布版本或自动升级项目。

人工编辑的正文继续有效。更新前完整读回，保留用户要求并导入新 Profile；核对当前正文 SHA-256，经过完整内容确认后使用 `--accept-current`。此参数不能跳过读取、导入和确认。0.2.0 的 Profile 与锁保持兼容，渲染格式不变。

## 公开边界

用户规则、个人 Profile、锁、候选、来源映射与运行日志只保存于用户指定私有环境，禁止进入本公开仓库的源码、模板、示例、测试或文档。记忆生成只在用户环境内进行，不调用外部服务处理个人记录。

公开规则与模板需明确用途、适用边界、稳定编号和版本；检查隐私、冲突与可执行性，用独立通用样例测试。向用户展示每份拟公开文件的全部内容，取得逐文件明确同意后才可加入公开目录。由个人偏好抽取或改写的公开内容同样需要审批。`--public-approved` 标志不能代替授权。

## 交付物审查与旧格式

实施前完整读取当前项目 `OPINION.md`，按条件选择适用条款；交付前逐条检查并修正明确问题。Profile 声明了分层加载时，改为先运行 `context core` 读取核心规则与规则束索引，任务命中触发条件或判断不清时用 `context bundle` 读取对应规则束，交付前用 `context check` 核对；命令返回 `fallback` 时完整读取正文。维护规则本身时始终完整读取。冲突改变交付时集中请用户裁决。用户反馈只形成候选，经确认才能发布新版本。项目需要记录候选发生次数、灰度使用与规则覆盖时，使用 `lifecycle` 命令在项目私有目录记账：任务结束后提交 `use` 事件，如实记录适用规则、逐条结果、读取的规则束和漏读；测试与演示标为 `fixture`。工具只记账，不在后台学习，也不自动晋升候选或把灰度版本转为正式，这些裁决来自用户。

旧格式 `templates/*.json`、`compose --template`、`compose --rule` 与 `compose --custom-file` 保持兼容。有锁项目必须使用版本化 Profile 流程，禁止用旧格式写入绕过核验；新项目优先使用版本化 catalog。

## 完成条件

- 选择从空白开始时，已有规则保持不变，不创建空规则版本；
- 其余入口展示完整结果，仅用户确认的规则进入正文；
- 精确来源、个人修改与排除条目可追溯，已发布版本不覆盖；
- 写后完整读回，`verify` 通过；失败与中断如实报告；
- 本 Skill 不创建 Case、不修改生命周期、能力清单或 Git 状态，不自行发布内容。
