# 与用户一起建立 SOP

SOP 里的细节（用什么工具、出错怎么办、中间产物放哪）是用户自己的习惯，每个人不同。建立时必须逐项谈清；谈不清的写成【待补充】留在草稿里，不得替用户补一个“合理的默认”。

## 流程概览

```text
说出想法 ─▶ 澄清场景与步骤 ─▶ 清点工具 ─▶ 谈清约定 ─▶ 展示完整草稿 ─▶ 用户确认 ─▶ 试跑一次 ─▶ 修订并启用
 （口述/粘贴/             （逐步追问）   （preflight）  （7 项问题，   （一次预览）    （decide）    （--trial）   （revise/activate）
  从 Case 提炼）                                       项目习惯只谈一次）
```

行业里对 SOP 的通行要素是目的、适用范围、职责、步骤、记录与修订控制（ISO 9001:2015 第 7.5 条对成文信息的版本与变更控制提出要求；条款细节未在本次会话核对）。好 SOP 的判断标准：没写过它的人也能照着执行；完成标准可检查；有版本和定期复核；偏离有记录。下面的谈话围绕这四点展开。

## 规则

1. **批量提问**：把需要用户回答的问题整理成“编号 + 问题”，一次发出，不逐条往返。`sop.py interview [<SOP>]` 给出标准问题清单与选项，并标出本项目习惯已覆盖的项。
2. **不替用户决定**：选项里的“推荐”只是倾向，用户可以改。用户没回答的项保持未确认。
3. **项目习惯只问一次**：出错、缺工具、中间产物、恢复、花钱步骤这五项是习惯，问清后 `sop.py defaults --set 键=值 … --apply` 写入项目习惯，以后新建 SOP 沿用；某个 SOP 有例外再单独 `decide --set`。
4. **用户给的实际做法优先于你的推断**：用户说“我平时用 X”，就写 X，即使你知道更常见的 Y。你认为有风险时说明风险，由用户决定。
5. **整个草稿一次预览、一次确认**：确认的是完整文件，不是零散片段。
6. **试跑**：启用前建议用 `run --trial` 实际走一遍，把暴露的问题改进 SOP 后 `revise`，再启用。

## 步骤一：场景与触发

问：这个流程在什么场景下用？不该用的相近场景是什么？有固定周期或事件吗？你平时会怎么说（给 1–2 句话）？
事件触发要追问范围：新建或关闭 Case 时要不要提示？是不是只针对带某些标签的 Case（例如只有带 `项目` 标签的 Case 关闭时才复盘）？不限定的话每个 Case 新建或关闭都会提示一次，通常太吵。
落到：`trigger` `exclude` `schedule` `on_events` `event_tags` `aliases` `examples_hit` `examples_miss`，以及一行 `description`。确认后 `decide --confirm trigger`。

## 步骤二：逐步追问

对用户说出的每一步，补齐这几项（不适用就跳过，不要硬凑）：

- 这一步的**输入**是什么，**产出**是什么？产出是最终成品还是中间产物？
- 用**什么工具**完成？有没有第二选择？
- 怎么判断这一步**做对了**（检查点）？
- 做错了**怎么办**（只在与全局约定不同时才写在步骤里）？
- 需不需要**用户确认**才能做（写入、外发、花钱、删除类步骤一律标“需确认：是”）？

用户只说了大意（“下载视频、转音频、转录”）时，你负责拆细并追问缺的信息，但拆出来的每个选择都要让用户确认，例如“下载用 yt-dlp 还是你有别的工具？”

## 步骤三：清点工具

1. 把全部步骤用到的工具汇总成前置条件清单：命令、Python 模块、模型文件路径、环境变量（只写变量名）、技能、MCP、需要手动确认的事（例如“已登录某账号”）。
2. 运行 `sop.py preflight`，把当前机器上的结果告诉用户：哪些就绪、哪些缺失、哪些你无法确认。
3. 工具因输入不同而不同时（例如 B 站视频用 yutto、其他站点用 yt-dlp），各自声明并写 `仅当`，避免用户为用不到的工具被要求安装。
4. 对每个缺失项问清：怎么装或怎么获取（写进 `安装`）、有没有替代方案（`替代`）、缺了怎么办（`缺失时`）。
5. 涉及**本地与云端二选一**的步骤（例如本地模型转录 vs 云端 API 转录）要问清：优先哪个；云端会把数据发给第三方，用户是否接受；密钥放在哪个环境变量。
6. 确认后 `decide --confirm requires`。

## 步骤四：谈清约定

用 `sop.py interview` 的前两项以外的五项（编号问题）。示例提问方式：

> 1. 某一步出错时怎么办？① 停下来告诉我（推荐）② 立即停止并保留现场 ③ 自动重试 N 次再问我 ④ 跳过继续、事后列出
> 2. 发现缺程序或缺模型时怎么办？① 停下来列清单等我处理（推荐）② 停止 ③ 跳过用到它的步骤 ④ 改用我声明的替代
> 3. 中间产物（下载的视频、转出的音频等）放哪里、完成后怎么处理？
> 4. 中途失败后重新执行，从哪里开始？
> 5. 花钱、耗时很长或占大量流量的步骤，要先问你吗？

用户的回答用 `decide --set` 或 `defaults --set` 写入。中间产物的位置如果在项目外，向用户确认该路径存在且有足够空间。

## 步骤五：预览、确认、试跑、启用

1. `sop.py new --slug … [--template …|--from-case …]` 生成草稿（预览 → `--apply`）；用编辑方式把谈好的内容填进 `SOP.md`，去掉所有【待补充】。
2. `sop.py validate <SOP>` 无错误；向用户**完整展示**草稿（不是摘要），说明哪些来自用户、哪些是你的建议。
3. 用户确认后 `decide`，再 `run --trial` 实际试跑一次；记录卡点，改进后 `revise`。
4. `activate` 前再确认一次；启用后写进索引，之后才会被触发。

## 从已完成的工作里提炼

用户说“这次做得不错，以后都这样”时：`sop.py new --slug … --from-case <Case>` 把该 Case 的工作记录变成草稿步骤，每步带【待补充】。你的工作是把“当时做了什么”改写成“每次都该怎么做”：去掉一次性细节，补上输入、产出、工具与检查点，再按以上步骤谈清约定。

## Agent 发现重复模式时

只提出候选：说明你看到了什么重复（哪几次、什么步骤），问用户是否要固化成 SOP。重复次数不等于确认，用户同意后才进入以上流程。

## 示例：处理一个视频

假设用户只说了个大意：“我想固化一个处理在线视频的流程，最后得到文字稿。”

需要追问并写进 SOP 的：下载用什么（yt-dlp？需要登录的站点怎么办？）、视频放哪、转音频用什么及参数（单声道 16 kHz？）、转录是本地模型还是云端 API（模型文件在哪、哪个环境变量放密钥、云端是否接受）、语言与是否要时间戳、成品文稿放哪及开头要记录哪些来源信息、中间文件（视频、音频、原始转录）完成后保留还是清理、某步失败怎么办、缺 ffmpeg 或模型时怎么办。随包样例 `video-to-transcript` 展示了完整写法，可作为起点：`sop.py new --slug … --template video-to-transcript`。
